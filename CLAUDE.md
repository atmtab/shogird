# CLAUDE.md — правила работы над Shogird

**Shogird** — платформа стажировок для студентов и IT-компаний Узбекистана. Хакатон-проект по гайду курса *Big Data* (`docs/BigData_3Week_Project_Guide.pdf`).

- **Что строим** описано в `SPEC.md`, это источник правды. Перед любой задачей читай нужный раздел SPEC.
- **Как строим** описано в этом файле.
- Если задача противоречит SPEC, остановись и спроси. Молча не отклоняйся от SPEC.

## Главный принцип

Команда должна уметь **объяснить каждую строку** на защите (требование гайда). Поэтому код пишется простым и явным, с минимумом абстракций и зависимостей. Комментарии пишутся **на русском** и объясняют *почему*, а не *что*. Идентификаторы пишутся на английском.

## Стек и ограничения

- Node.js 20+, Express 4, ES-модули (`"type": "module"`), **без TypeScript и без сборки**.
- Зависимости: только `express`, `pg`, `mongodb`, `dotenv`, `bcryptjs`, `jsonwebtoken`, `cookie-parser`. **Любую новую зависимость согласуй со мной заранее.**
  - Используем `bcryptjs`, а не `bcrypt`: нативный `bcrypt` часто не собирается на Windows в лабораториях.
- Фронтенд: чистые HTML + CSS + JS (`fetch`). Никаких React, Vue, Tailwind, jQuery и ORM. Chart.js тоже не используем: он в списке «вне объёма» (SPEC §15), графики делаются на CSS.
- Две базы: PostgreSQL и MongoDB. Распределение данных между ними задано в SPEC §3 и не меняется без согласования.

## Окружение разработчика

- Основная машина: **Windows** (PowerShell / cmd, VS Code). PostgreSQL и MongoDB установлены локально как службы (`localhost:5432`, `localhost:27017`).
- npm-скрипты должны быть кроссплатформенными: никаких `rm -rf`, `cp`, `VAR=x cmd`. Нужна файловая операция — пиши маленький Node-скрипт в `server/scripts/`.
- Если служба БД не запущена, а `psql` или `mongosh` не установлены, **сообщи мне и предложи, что сделать**. Сам службы не устанавливай и не настраивай.
- `.env` создаётся из `.env.example`. **Пароль PostgreSQL не придумывай, спроси меня.**

## Команды (из папки `server/`)

```bash
npm install
npm run dev            # node --watch src/server.js → http://localhost:3000
npm start              # node src/server.js (для Render)
npm run db:create      # создать базу shogird, если её нет
npm run db:reset       # выполнить sql/01_schema.sql + sql/02_seed.sql (СТИРАЕТ ДАННЫЕ)
npm run db:bigdata     # выполнить sql/04_big_data.sql (500k строк, медленно)
npm run seed:mongo     # пересоздать коллекции Mongo и сгенерировать данные (СТИРАЕТ ДАННЫЕ)
npm run smoke          # сквозная проверка API (сервер должен быть запущен)
npm run i18n:check     # сверка ключей словарей ru/uz/en
```

**Защита от потери данных:** `db:reset` и `seed:mongo` должны отказываться работать, если `DATABASE_URL` или `MONGODB_URI` указывают не на `localhost`/`127.0.0.1`. Исключение: явно переданный флаг `--cloud`. **Никогда не запускай их с `--cloud` без моего прямого подтверждения в чате.**

## Правила кода

### SQL (PostgreSQL)
- **Только параметризованные запросы** (`$1, $2…`). Конкатенация или шаблонные строки с пользовательскими данными внутри SQL запрещены без исключений.
- Транзакции пишутся по шаблону гайда: `const client = await pool.connect()` → `BEGIN` → … → `COMMIT`; в `catch` выполняется `ROLLBACK` и ошибка пробрасывается дальше; в `finally` вызывается `client.release()`.
- Проверку и изменение делай **одним** запросом (`UPDATE … WHERE seats_left > 0 RETURNING …`, `UPDATE … WHERE is_booked = false …`). Отдельный `SELECT` для проверки создаёт гонку.
- Деньги хранятся только в `NUMERIC(12,2)`, никогда во `FLOAT`. `pg` возвращает NUMERIC строкой, поэтому в JS приводи через `Number()`, а в статистике используй `::float` / `::int`.
- `SELECT *` в роутах не используй, перечисляй нужные колонки.
- Скрипты `01_schema.sql` и `04_big_data.sql` должны быть перезапускаемыми (`DROP … IF EXISTS` в начале).

### MongoDB
- Числовые ID (`studentId`, `vacancyId`, `companyId`) совпадают с ID в PostgreSQL. ID из `req.params` приводи через `Number()`.
- Аналитические события пишутся **после** `COMMIT` и **без `await`**: `.catch(e => console.error(...))`. Сбой логирования не должен ломать запрос пользователя. Для этого есть единый хелпер `lib/events.js`.
- Генераторы данных детерминированные (фиксированный seed PRNG), а даты задаются относительно текущего момента.

### API
- Каждый async-роут оборачивается в `wrap()`. Единый обработчик ошибок отвечает `{ error, code }`.
- Ошибки создаются через хелпер `httpError(status, code, message)` из `lib/errors.js`. Коды и статусы перечислены в SPEC §9.6, новые коды добавляй туда же.
- Валидация на сервере обязательна для всех входных данных (обязательные поля, типы, диапазоны, допустимые enum-значения). Клиенту не доверяем.
- Авторизация: `requireRole(...)` на каждом роуте кабинетов. Компания работает только со своими сущностями, на чужой ID отвечаем 404.
- Переходы статусов заявок описаны **в одном месте**, в `lib/statuses.js` (SPEC §6.1).
- Роуты разбиты по файлам в `src/routes/`, файл `server.js` остаётся тонким.

### Фронтенд
- **Никакого текста интерфейса в HTML/JS напрямую.** Только ключи i18n (`data-i18n="..."` или `t('...')`). Новый ключ добавляется **сразу во все три словаря** (`ru`, `uz`, `en`), после чего запускается `npm run i18n:check`.
- Узбекский пишется латиницей с символом **ʻ** (U+02BB): *oʻ, gʻ, soʻm*.
- Любой текст из базы или от пользователя вставляется в `innerHTML` только через `esc()`.
- `localStorage` используется только для языка (`shogird.lang`), обращения обёрнуты в try/catch. Авторизация живёт в httpOnly cookie, токен в JS не хранится.
- Ошибки API показываются через `t('err.' + code)` с фолбэком на `error`.
- Mobile-first, ширина 360 px без горизонтального скролла. Цвета задаются CSS-токенами из SPEC §10.4.

### Данные
- Компании в сиде **вымышленные**. Не используй реальные бренды и логотипы.
- Реальные персональные данные не используются. Email-адреса только на `example.uz`.
- Секреты не попадают в код и в git. `.env` и `node_modules` должны быть в `.gitignore`.

## Порядок работы

1. Работаем **по фазам** из SPEC §16. В начале фазы покажи короткий план файлов и дождись моего «ок».
2. Внутри фазы двигайся маленькими шагами: изменил что-то и сразу проверил (запуск скрипта, запрос к API, открытие страницы).
3. В конце фазы прогони критерии приёмки, отметь `[x]` в SPEC §16 и сделай коммит `Phase N: <кратко>`. **Push только по моей просьбе.**
4. После фазы дай отчёт в 5–10 строк: что сделано, как проверено, что осталось, какие решения стоит обсудить. Следующую фазу без моего подтверждения не начинай.
5. Если нашёл противоречие или пробел в SPEC, предложи правку SPEC, а не обходи её в коде.

## Чего не делать

- Не добавлять функции из SPEC §15 без просьбы.
- Не «улучшать» схему БД после закрытия Фазы 1 без согласования, потому что от неё зависят сид, запросы и отчёт.
- Не переписывать рабочий код ради стиля.
- Не запускать разрушающие команды против облачных БД.
- Не коммитить `.env`, дампы и большие сгенерированные файлы.
