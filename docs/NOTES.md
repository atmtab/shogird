## 2. Порядок команд (из папки `server/`)

```
npm install
npm run db:create       # создать базу shogird
npm run db:reset        # схема + сид (СТИРАЕТ ДАННЫЕ)
npm run seed:mongo      # Mongo: 60 000 событий, 30 000 поисков, 40 резюме, 40 отзывов (СТИРАЕТ ДАННЫЕ)
npm run dev             # http://localhost:3000
npm run smoke           # 143 проверки; сам делает db:reset
npm run db:bigdata      # 500 000 строк + EXPLAIN до/после индекса (~7 секунд)
```

Важно: `seed:mongo` читает ID из PostgreSQL, поэтому сначала `db:reset`. После `smoke` в PG остаётся изменённое состояние, для чистого демо снова `db:reset` и `seed:mongo`.

## 3. Замеры для отчёта

**PostgreSQL, `04_big_data.sql`:** запрос «backend-заявки в Ташкенте за 30 дней» по 500 000 строк.

| | План | Время выполнения |
|---|---|---|
| До индекса | Parallel Seq Scan | 68,4 мс (три прогона: 65–150 мс) |
| После `idx_archive_dir_city_date (direction, city, applied_at)` | Bitmap Index Scan | 1,0 мс (три прогона: 2,8–3,1 мс) |

Сезонность в архиве: май–июль по 45–47 тысяч заявок в месяц, остальные месяцы около 12 тысяч.

**MongoDB, `02_queries.mongodb.js`:** `events.find({direction:'backend', type:'apply'})`.

| | План | Просмотрено документов | Время |
|---|---|---|---|
| До индекса `{direction, type}` | IXSCAN по `{type, ts}` | 8 896 | 17 мс |
| После | IXSCAN по `{direction, type}` | 1 145 | 4 мс |

Гонка за последнее место (T3): два параллельных `accept` дают `[200, 409 NO_SEATS]`.

## 4. Решения и отклонения от SPEC

| # | Решение | Почему |
|---|---|---|
| 1 | JSON API в **camelCase** (`seatsLeft`, `isItparkResident`), БД в snake_case | Привычно для фронтенда. Предлагается дописать в SPEC §9 |
| 2 | Фильтр `skill` каталога принимает **название** навыка, можно через запятую (все должны быть у вакансии, максимум 5) | В `search_logs` навыки хранятся названиями |
| 3 | Роуты студента смонтированы на `/api` (пути `/api/me/*`, `/api/applications/:id/*`), роуты компании на `/api/company` | Так записано в SPEC §9 |
| 4 | Компания из `shortlisted` может только отклонить; в `interview` заявку переводит студент бронью слота (T2) | Диаграмма SPEC §6.1. Таблица переходов только в `lib/statuses.js` |
| 5 | Рекомендации (#13) включают вакансии, на которые студент уже откликнулся, с полем `applicationStatus` | SPEC не требует их исключать |
| 6 | Тип DATE из PG читается строкой `YYYY-MM-DD` | Иначе `deadline` сдвигался на день из-за часового пояса (UTC+5). Исправлено в `db.js` |
| 7 | Для неизвестного email при входе всё равно выполняется `bcrypt.compare` с фиктивным хэшем | Время ответа не выдаёт, есть ли аккаунт |
| 8 | `withTransaction()` в `db.js` реализует шаблон гайда `BEGIN → COMMIT → ROLLBACK → release` | Не повторять шаблон в каждом роуте |
| 9 | Валидаторов схемы Mongo нет | `drop()` в сид-скрипте всё равно стирал бы их; гибкость структуры и есть причина выбора Mongo |
| 10 | Индексы Mongo описаны и в `01_setup.mongodb.js`, и в `seed-mongo.js` | Сид должен работать без mongosh. Мелкое сознательное дублирование |
| 11 | Название компании при дубликате при регистрации возвращает `400 VALIDATION` | В §9.6 нет отдельного кода. Можно добавить `COMPANY_TAKEN` |
| 12 | Ошибка парсинга JSON тела запроса возвращает `400 VALIDATION` | Единый формат `{ error, code }` |
| 13 | `GET /api/vacancies` выдаёт только открытые и не просроченные по `deadline` | Просроченную вакансию в каталоге показывать нельзя |

## 5. Открытые вопросы (нужно решение владельца)

1. **Отзывы в Mongo сиде.** По §6.5 отзыв может оставить только студент с `accepted`-заявкой, а в PG таких 4. В Mongo ~40 отзывов: 4 настоящих, ещё 36 «исторические» (пары выбраны случайно, в PG не подтверждены). Оставить так и сказать об этом на защите, или оставить только 4?
2. **Популярность вакансий в событиях.** Распределение Ципфа крутое: вакансия 16 набрала 4 095 просмотров за 30 дней. Смягчить, если на дашборде будет выглядеть странно.
3. **Порядок демо D1 + D2.** Если оффер принимает Азиза, её собеседование из D1 отменяется (правило T3). Поэтому в демо оффер сначала принимает **Бекзод**, и Азиза получает `NO_SEATS` (записано в README).
4. **Rate limit** для `/api/auth/login` не сделан (нужна зависимость, вне списка). Для хакатона допустимо, но возможен вопрос на защите.
5. **Дедлайны в сиде** заданы как «сегодня + N дней», поэтому через 15–50 дней вакансии начнут выпадать из каталога. Для демо запускать `db:reset` непосредственно перед показом.
6. **Статус `offer` без проверки мест.** Компания может выдать оффер, когда `seats_left = 0`; тогда студент получит `NO_SEATS` при принятии. Это и есть демо D2, но в реальном продукте стоит предупреждать компанию.
